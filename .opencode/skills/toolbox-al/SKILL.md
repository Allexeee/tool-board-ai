# toolbox-al

Порядок решает приложение, слова — ты. Не пересчитывай очередь сам: вызывай `dispatch` и бери то, что он выдал.

## RUN: как ведёт себя оркестратор

1. **Разбор запросов на план.** Пока план не ясен — исполнение не начинается. План: этапы, задачи, DoD, области, порядок.
2. **Автономное исполнение.** Нарезка, руки, субагенты, слияние этапов в dev. Решение владельца не останавливает конвейер: такой пункт откладывается и ждёт.
3. **Конец RUN** — остановка владельцем, задачи закончились, нужно решение владельца.
4. **Отчёт.** Сделано, ждёт залития в main (с ценой и рисками), нужны решения, взятые допущения.

Оркестратор не берёт задачи на исполнение: его дело — план, нарезка, раздача, ревью и отчёт; работают worker-1 и worker-2.

**Запуск прогона.** Владелец пишет «RUN» — система задаёт три вопроса (режим отдельно не выбирается, он следует из ответа №2):

1. Какие запросы — можно комбинировать конкретные с объёмом:
   - конкретные: берутся первыми;
   - ближайшие: после отмеченных добираются 1-2 верхних по приоритету; без отмеченных — только они;
   - **доталово**: всё возможное до упора; в паре с конкретными сначала они, затем всё остальное;
   - ближайшие и доталово **взаимоисключающие**: при выборе обоих система прямо говорит об этом и просит перевыбрать, а не угадывает;
   - свой ответ.
2. Утверждать начальный план: да → утверждается только начальный план по разбираемым сейчас запросам, все следующие исполняются без утверждения; нет → автономно до упора.
3. Питание после прогона: ничего / гибернация / выключение.

У каждого вопроса есть предлагаемый ответ по умолчанию: ближайшие, не утверждать, питание не трогать.

**Новая задача от владельца во время прогона**, не связанная с текущими планами: по умолчанию оформляется запросом, а не берётся в работу; затем владельцу задаётся вопрос — включать ли запрос в текущий прогон. Без ответа не включается. Найденные по ходу запросы, не от владельца, разбираются и реализуются сразу, если не требуют его решения.

**Два режима прогона:**
- **по плану** — система показывает нарезку, владелец утверждает план, дальше задачи режутся, раздаются и выполняются автоматически, включая созданные по ходу; запросы вне плана копятся.
- **доталово** — автономный: при запуске спрашивается, утверждать ли начальный план; дальше исполняется всё возможное, включая новые запросы, пока не упрётся.

**Питание после автопрогона.** Не вопрос на каждый запуск, а явная опция в команде: «после рана ПК в гибернацию» / «после рана выключить». Если задана — выполняется сразу после отчёта, ждать владельца не нужно (прогон запускался на ночь). Критическое из ревью правится, это и есть конец рана, затем питание. Гибернация — локальный таймер 90 секунд с отменой, иначе выключение. Отчёт пишется на диск до питания.

**Ревью привязано к релизу:**
- остановка владельцем — ревью не было, код не проверен; перед релизом ревью предлагается, и отчёт это говорит;
- задачи кончились или нужен владелец — в конце прогона ревью всего нерелизнутого dev, критическое правится до отчёта, и тогда RUN готов к релизу.

**Релиз не входит в RUN.** Только по команде владельца: прогон заканчивается отчётом, `release` — отдельная команда.

## Порядок работы

1. `al_now` или `node bin/toolbox-al.ts now` — что происходит.
2. `al_task` или `task show <id>` — контекст задачи: DoD, область, зависимости.
3. `al_take` или `take <id> --as <исполнитель>` — взять в работу.
4. Работаешь.
5. `al_done` или `done <id> --as <исполнитель> --summary "что сделано" --checks "чем проверено"`.
6. Если сделать нельзя — `al_block` с причиной из списка: `needs_data`, `needs_access`, `needs_decision`, `impossible`, `budget_exceeded`.

## Правила

- **Не коммить и не создавать ветки.** Коммит делает приложение командой `done`, только по файлам своей области.
- **Не менять чужие руки.** Руку правит сам исполнитель или оркестратор.
- **Не менять ранг фичи.** Ранг — решение владельца.
- **Не закрывать задачу без отчёта.** Задача без отчёта не закрывается.
- **Не ревьюить свою задачу.** Вердикт даёт другой исполнитель или владелец.
- **Не обходить ревью.** Задача с `review` уходит в `in_review`, а не в `done`.

## Команды

| Команда | Что делает |
|---|---|
| `now` | фичи, этапы, кто что держит |
| `inbox` | что ждёт человека |
| `next --as w1` | что делать дальше |
| `take <id> --as w1` | взять задачу |
| `touch <id> --as w1` | продлить аренду |
| `save <id> --summary` | черновик |
| `done <id> --as w1 --summary` | закрыть с отчётом |
| `block <id> --as w1 --reason --note` | прервать |
| `ask <subject> "вопрос" --to owner` | спросить |
| `answer <Q> "ответ"` | ответить |
| `dispatch` | кому что достаётся |
| `cal --days 7` | расписание |
| `friction` | где система сопротивляется |

## Просьбы владельца

Если владелец просит «добавь фичу» — это запрос, а не задача. Собери план: вопросы один раз, затем план с допущениями, затем `plan approve` и `plan apply`. Не создавай задачи по одной вручную, если есть план.
