# now: задачи по агентам, вероятные забеги и теги

Дата: 2026-11-22
Карточка: NOW-2

## Зачем

После NOW-1 `now` показывает задачи агентов, но потерял вероятные забеги.
Владелец хочет видеть:

- `now 0` — свои задачи и то, что ждёт его решения;
- `now 1` — задачи текущего агента и вероятные забеги, включая запросы;
- `now 2` — задачи других агентов, включая ещё не назначенные;
- `now 3` — запросы и общую очередь (остаётся).

Забеги должны иметь формальные варианты, а не собираться произвольно.
Запросы должны уметь входить в забег и разбираться первыми.

## Цели

- `now` по умолчанию открывает вкладку 0.
- `now 1` показывает на руках, очередь и три вероятных забега.
- `now 2` показывает только других агентов, без текущего.
- Карточки получают теги, по которым строятся забеги.
- Забег бывает трёх вариантов: новое, улучшение, после ревью.
- В каждом варианте — до трёх слотов; слот задаётся порядком карточек в забеге.
- Запрос может быть в забеге; он помечается и разбирается до работы.
- После нарезки запросов в забеге approve владельца не требуется.

## Не входит

- Отдельная сущность «вариант забега» в базе: вариант — это правило и тег.
- Fallback-карточки и fallback-пул: если карточек меньше трёх, забег короче.
- Явные слоты на карточке: слот — параметр забега, не карточки.
- Автоматическая расстановка тегов по тексту запроса.
- Цвета где-либо, кроме `now`.

## Подходы

### Хранение категории

1. **Свободные `tags: string[]` на карточке.** Агент ставит теги; три
   стандартных тега (`new`, `improve`, `review`) определяют вариант забега.
   Гибко, не ломает другие теги, требует миграции схемы.
2. **Фиксированный `kind: new | improve | review`.** Проще, но не даёт
   добавить свои категории и смешивает категорию с прочими метками.
3. **Соглашение в группе или заголовке.** Без миграции, но хрупко и мешает
   свободно менять группы.

Выбран **1**: владелец хочет, чтобы агент ставил теги и мог менять правила
формирования забегов.

### Запрос в забеге

1. **Показ только.** Запрос виден в вероятном забеге, но реальный `run start`
   его не берёт. Не соответствует требованию «запрос может существовать в
   ране».
2. **`planned` + разбор вперёд.** Запрос добавляется в забег как `planned`, не
   меняя фазу; `run next` возвращает его первым, агент пишет spec, затем
   карточка становится задачей в этом же забеге.
3. **Сразу задача.** `run start` переводит запрос в задачу и бронирует, минуя
   разбор. Теряется spec.

Выбран **2**.

### Approve после нарезки

1. **Ждать approve владельца.** Сохраняет текущий гейт, но противоречит
   выбранному потоку «показал спеки и продолжил».
2. **Продолжать без approve.** Агент разбирает запросы, показывает спеки и
   начинает работу; владелец может остановить забег. Выбран владельцем.
3. **Пакетный approve.** Владелец утверждает все запросы забега одним
   действием. Ближе к гейту, но всё равно ждёт владельца.

Выбран **2**. Это осознанный компромисс: гейт approve для запросов внутри
забега снимается, но spec показывается и забег можно остановить.

## Данные

### Теги карточки

- `cards.tags text not null default '[]'` — JSON-массив, как `scope`.
- `Card.tags: string[]`.
- `NewCardInput.tags?`, `CardPatch.tags?`, `ShapeFile.tags?`.
- Нормализация: trim, нижний регистр, дедупликация, пустые отбрасываются.
- `card add|edit --tag new --tag backend`; `card edit --tag` **заменяет** весь
  список, `--clear-tags` очищает. `card show` печатает теги; `ShapeFile.tags`
  тоже заменяет список.
- `addFinding` ставит `review` автоматически: находка ревью — это действие
  после ревью.
- Схема v3: миграция добавляет колонку; существующие карточки получают `[]`.
  Находки с `origin_card_id` дозаполняются тегом `review` при миграции.

### Варианты забега

Три стандартных тега и подписи:

| Тег | Подпись | Смысл |
| --- | --- | --- |
| `new` | НОВОЕ | новая функциональность |
| `improve` | УЛУЧШЕНИЕ | улучшение существующего |
| `review` | ПОСЛЕ РЕВЬЮ | исправления и действия после ревью |

Карточка может иметь несколько тегов. Для забега берётся первый вариант из
порядка `new`, `improve`, `review`; так один забег не пересекается с другим.
Карточка без ни одного из этих тегов в вероятные забеги не попадает, но
остаётся в списках задач. `now 1` показывает счётчик «без тега», чтобы это
было видно.

### Запрос в забеге

- `run_cards.status` получает значение `planned` для запросов.
- `startRun` принимает карточки фазы `task` (как сейчас) и фазы `request` со
  статусом `new` (без держателя) или `shaping` (держатель — этот же
  исполнитель). `approval` — не кандидат: это задача, уже ждущая владельца.
- Запрос не бронируется и не меняет фазу/статус/держателя, но получает
  `cards.run_id = забег`: так `block`/`cancel`/`drop` находят его строку в
  `run_cards`, а `suggestRuns` не предлагает его повторно.
- Задача бронируется как сейчас (`booked`, holder, lease).
- Порядок `run_cards.position` = слоты 1..N. Запрос занимает слот наравне с
  задачей и входит в `run_size`.
- `run add <запрос>` добавляет `planned`, `run drop <запрос>` снимает и
  очищает `run_id`.

## Правила забегов

### Вероятные забеги в `now 1`

Для текущего исполнителя строятся три предложения — по одному на вариант.

1. Кандидаты: карточки, подходящие по навыку; запросы в `new` без держателя
   или `shaping` с держателем = текущий агент; задачи в `ready`/`waiting` без
   держателя и с `position`. `approval` не кандидат.
2. Зависимости: карточка `waiting` попадает в забег, только если её
   незакрытые зависимости уже закрыты или входят в этот же забег раньше по
   порядку. Если зависимость не удовлетворить — карточка пропускается.
3. Вариант карточки — первый тег из `new`, `improve`, `review`.
4. Внутри варианта: сначала запросы (их надо разобрать), затем задачи по
   `position`. Запросы между собой — по `created_at`, задачи — по `position`.
   Если порядок нарушает зависимость, карточка пропускается.
5. Взять до `run_size` карточек (по умолчанию 3, максимум 3). Запросы
   занимают слоты наравне с задачами.
6. Если карточек меньше — забег короче. Fallback нет, чужие варианты не
   добираются.
7. Забеги не пересекаются: карточка попадает только в свой вариант.
8. Предложение ничего не бронирует.
9. `--group`/`--skill` сужают и задачи, и кандидатов в забеги.
10. `now 1 --as owner` не строит забеги: владельцу показывает подсказку
    «смотри now 0», потому что `now 0` — его вкладка.

`run_size` исполнителя остаётся потолком. Три варианта — три независимых
предложения, а не один забег на девять карточек.

### Реальный забег

```bash
board run start --as worker-0 --cards NOW-3,CORE-5,REVIEW-2
board run start --as worker-0 --suggest 2
```

- Порядок `--cards` = слоты 1, 2, 3. Отдельного поля слота нет.
- `--suggest <n>` берёт n-е вероятное предложение (1 — новое, 2 — улучшение,
  3 — после ревью).
- В забеге может быть 1..`run_size` карточек; запросы разрешены.
- Запросы в забеге обрабатываются первыми, независимо от слота.

### Разбор запроса в забеге

1. `run start` добавляет запрос как `planned`.
2. Агент сообщает, какие карточки взял, и что в забеге есть запросы без плана.
3. `run next` возвращает первый `planned`-запрос с признаком `request`.
4. Агент берёт его: `board take <ID> --as <агент>`.
   - Если запрос в `new`, `take` переводит его в `shaping` (держатель, lease)
     и возвращает подсказку «заполни spec».
   - Агент пишет spec/acceptance/scope/оценки, непонятные места — `ask`/`block`.
   - Повторный `take` того же запроса после spec выполняет **promotion**.
5. Promotion проверяет spec, acceptance, skill, оценки и scope (если нужен
   merge), затем делает то же, что обычный `take`: создаёт ветку/worktree,
   ставит `in_progress`, holder, run_id, продлевает lease забега и соблюдает
   правило «одна карточка в работе на забег». Без этого `finish` не сможет
   закрыть карточку с `needs_merge=true`.
   - `run_cards.status` = `in_progress`;
   - событие `card.promoted` с пометкой, что approve пропущен по правилу
     забега.
6. Если есть открытые вопросы или карточка `blocked`, `run next` её
   пропускает. После ответа владельца запрос возвращается в голову очереди
   `planned`-запросов этого забега, даже если его слот был позже.
7. `run end` возвращает неразобранные `planned`-запросы в фазу `request` без
   изменений и очищает `run_id`; забег закрывается с пометкой о снятых
   запросах.
8. Если разобранная карточка позже вернётся в `ready`/`waiting` (block,
   reopen, истёкший lease), ей назначается позиция в очереди: promotion не
   оставляет задачу с `position = null`.

Спецификация запроса в забеге не проходит `submit`/`approve`, поэтому
spec review не запускается. Агент делает self-check по skill; владелец видит
spec в `card show` и может остановить забег.

## Вкладки

### now 0 — по умолчанию

```
[0] ЗАДАЧИ ДЛЯ МЕНЯ
УТВЕРДИТЬ (n)
  ID  заголовок  навык  важность/срочность
ЗАДАЧИ (n)
  ID  заголовок
ВОПРОСЫ (n)
  ID  текст  спрашивает агент
```

- `approvals`: задачи в `approval`.
- `ownerCards`: навык `owner`, статусы `ready` и `waiting` (очередь владельца).
- `questions`: открытые вопросы.
- Имя исполнителя в конце строк задач не печатается: в этой вкладке это всегда
  владелец.
- Без изменений в данных, кроме `waiting` в ownerCards.

### now 1 — текущий агент

```
[1] МОИ ЗАДАЧИ
НА РУКАХ (n)
  ID  заголовок  статус
ОЧЕРЕДЬ (n)
  pos  ID  заголовок  статус
ВЕРОЯТНЫЕ ЗАБЕГИ
  НОВОЕ
    ?  NOW-3  Добавить форму
       CORE-5  Починить ...
  УЛУЧШЕНИЕ
    ...
  ПОСЛЕ РЕВЬЮ
    ...
```

- Карточка в забеге — отдельная строка: `[?] ID  заголовок`.
- `?` — запрос; в TTY он жёлтый. Задачи — пробел в этой колонке.
- Имя текущего агента в заголовке не печатается: его задаёт `--as` и он есть
  в JSON.
- Пустой вариант не печатается.
- «Без тега: n» — если у агента есть задачи без вариантного тега.
- Забеги — предложения, не бронирование.

### now 2 — другие агенты

```
[2] ЗАДАЧИ ДРУГИХ АГЕНТОВ
worker-1  backend
  НА РУКАХ (n)
  ОЧЕРЕДЬ (n)
worker-2  backend
  ...
```

- Текущий `--as` исключается.
- Только задачи: на руках + очередь по навыкам. Вероятных забегов нет.
- Агенты без задач не печатаются; если задач нет ни у кого — «задач нет».

### now 3 — запросы и очередь

Без изменений: открытые запросы, общая очередь, лимиты и счётчики.

## JSON

- `now 0`: `{ view, header, approvals, ownerCards, questions }`.
- `now 1`: `{ view, header, executor, skills, current, queue, probableRuns, untagged }`,
  где `probableRuns: [{ tag, label, cards: [{ card, request }] }]`.
  Пустые варианты в JSON не попадают; `untagged` — число задач без
  вариантного тега. `--group`/`--skill` сужают current, queue и кандидатов в
  забеги.
- `now 2`: `{ view, header, executors: [{ id, skills, current, queue }] }`.
- `now 3`: без изменений.
- `Card.tags` есть во всех карточках JSON.

## Миграция

1. Схема v3 добавляет `tags`, существующие карточки — `[]`.
2. Находки (`origin_card_id != null`) получают `review`.
3. Остальные карточки тегирует агент при разборе; до этого они видны в
   задачах, но не в вероятных забегах.
4. `now` по умолчанию меняется с 2 на 0; README, skill и AGENTS.md
   обновляются.
5. Старые забеги без `planned`-карточек читаются как раньше.

## Риски

- **Снятый approve.** Запрос в забеге идёт в работу без утверждения
  владельца. Компенсация: spec показывается, событие пишется, забег можно
  остановить. Если это окажется слишком рискованно, правило меняется на
  «ждать approve».
- **Нет тега — нет забега.** Забытая тегия оставляет карточку вне вероятных
  забегов. Компенсация: счётчик «без тега» в `now 1`.
- **Несколько тегов.** Берётся первый по порядку `new`, `improve`, `review`;
  иначе карточка могла бы попасть в два забега.
- **Три забега по три карточки.** Это предложения, а не бронирование; они не
  занимают руки и не мешают другим.
- **`run_size` меньше трёх.** Забег будет короче; fallback нет.
- **Planned-запросы и lease.** Просроченный забег должен вернуть `planned`
  запросы в фазу `request`, а не потерять их.

## Решения после проверки исполнителем

Свежий исполнитель задал 11 вопросов. Решения приняты и внесены выше:

1. **Триггер promotion.** `take <ID>` на `planned`-запросе: первый вызов
   переводит в `shaping`, второй — в `in_progress`. Отдельной команды нет.
2. **Ветка и lease.** Promotion идёт тем же путём, что обычный `take`: ветка,
   worktree, lease забега, одна карточка в работе.
3. **Состояния кандидатов.** Запросы — `new` без держателя или `shaping` с
   держателем = агентом; задачи — `ready`/`waiting`. `approval` не кандидат.
4. **Planned на карточке.** `cards.run_id` заполняется, фаза/статус/держатель
   не меняются; `block`/`cancel`/`drop` находят запись в `run_cards`;
   `suggestRuns` не предлагает повторно.
5. **Зависимости.** Старое правило `depsStartable` сохраняется: `waiting`
   попадает в забег, только если зависимости закрыты или раньше в забеге.
6. **`--as owner`.** `now 1` для владельца не строит забеги и подсказывает
   `now 0`.
7. **Семантика `--tag`.** Заменяет список; `--clear-tags` очищает;
   `ShapeFile.tags` заменяет.
8. **Пропуск в `run next`.** Пропускаются `blocked` и карточки с открытыми
   вопросами; после ответа запрос возвращается в голову `planned`-очереди.
9. **Позиция после promotion.** Если карточка вернётся в `ready`/`waiting`,
   ей назначается позиция в очереди; `position = null` не остаётся.
10. **`run_size`.** Запросы занимают слоты наравне с задачами и входят в
    лимит.
11. **JSON.** Пустые варианты не отдаются; есть `untagged`; `--group`/`--skill`
    сужают задачи и кандидатов.

## Критерии приёмки

1. `board now` без аргумента открывает `[0] ЗАДАЧИ ДЛЯ МЕНЯ`; в JSON `view: 0`.
2. `now 0` содержит approvals, owner-задачи в `ready`/`waiting` и открытые
   вопросы; в строках задач нет имени исполнителя в конце.
3. `now 1 --as <агент>` содержит current, queue и три вероятных забега
   (`new`, `improve`, `review`) по до `run_size` карточек; забеги не
   пересекаются; в заголовке нет имени исполнителя.
4. В `now 1` запрос в забеге помечен `?` и жёлтым в TTY; каждая карточка —
   отдельная строка `[?] ID  заголовок`.
5. `now 2` исключает текущего `--as` и показывает только задачи других
   агентов, без забегов.
6. `now 3` работает как раньше.
7. `card add|edit --tag` сохраняет теги; `--tag` заменяет список,
   `--clear-tags` очищает; `card show` их печатает; находки ревью
   автоматически получают `review`.
8. `run start --cards A,B,C` принимает запросы, сохраняет порядок как слоты,
   добавляет их как `planned` с `run_id` и считает их в `run_size`.
9. `run next` возвращает `planned`-запросы первыми; `take` переводит запрос в
   `shaping`, повторный `take` после spec — в `in_progress` с веткой,
   worktree и lease; approve не требуется. При вопросах или `blocked` запрос
   пропускается и после ответа возвращается в голову `planned`-очереди.
10. `run end` возвращает неразобранные запросы в фазу `request` и очищает
    `run_id`; разобранная и отпущенная карточка получает позицию в очереди.
11. `--as owner` в `now 1` не строит забеги и подсказывает `now 0`.
12. Зависимости: `waiting`-карточка не попадает в забег, если её зависимость
    не закрыта и не идёт раньше в том же забеге.
13. JSON: пустые варианты не отдаются, `untagged` заполнен,
    `--group`/`--skill` сужают задачи и кандидатов.
14. Тесты: unit на правила забегов, теги, зависимости и planned-запросы; CLI
    на вкладки, default 0 и разбор запроса; e2e на забег с запросом.
15. README, skill и `docs/board/terminology.md` описывают теги, три варианта,
    слоты и поток запроса в забеге.
