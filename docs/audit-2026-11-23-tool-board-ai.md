# Аудит tool-board-ai 1.4.0

Дата: 2026-11-23  
Предмет: доска карточек `tool-board-ai` (CLI + OpenCode-интеграция)  
Статус на момент аудита: `package.json` 1.4.0, `HEAD` = `3e6d0fd` (release), последний тег — `v1.3.0`.

## Как проверял

- Прочитаны `src/core/**`, `src/cli/**`, `bin/board.ts`, `.opencode/**`, `README.md`, `CHANGELOG.md`, `docs/board/terminology.md`, тесты.
- Прогнан полный набор: `node --test` — **433/433 зелёных, 48 с**.
- `board doctor` — «всё в порядке», код выхода 0.
- Выполнены реальные команды на текущей доске: `now`, `card show`, `card list`, `run list`, тайминги.
- Проверены git-теги локально и на `origin`, синхронность сгенерированных `.opencode`-файлов с шаблонами в `src/core/opencode.ts`.
- Состояние доски: 109 карточек, 34 забега, 75 ревью, 1177 событий, `.board/board.db` — 3,9 МБ.

## Короткий ответ

Ядро зрелое и хорошо спроектированное. Для целевого сценария (один владелец, 1–3 агента, один git-репозиторий, локальная машина) инструмент **уже пригоден к ежедневной работе**.

Но **выпуск 1.4.0 сейчас не готов к установке в новые проекты**: тега `v1.4.0` нет ни локально, ни на `origin`, поэтому `board init` поставит `v1.3.0` — на 83 коммита назад. Это главный блокер. Плюс есть несколько эксплуатационных дыр (бэкапы, CI, конкурентность, документация), которые надо закрыть до того, как называть инструмент «полноценным».

## Сильные стороны

1. **Домен живёт в коде, а не только в документации.**
   Состояния, переходы, `spec`/`acceptance`, `spec_rev`, `scope`, зависимости, owner-карточки проверяются в `lifecycle.ts`, `runs.ts`, `review.ts`. Нельзя случайно проскочить approve, сдать карточку без критериев приёмки или смержить файлы вне scope.

2. **Данные.**
   SQLite + WAL, `begin immediate`, вложенные транзакции, миграции схемы v1→v3 с версией и защитой «база новее инструмента», журнал событий, человекочитаемые ID без переиспользования.

3. **Git-механика.**
   Worktree на исполнителя, ветка на карточку, проверка diff по scope, `merge --no-ff` в `dev`, revert при отмене, аккуратный abort конфликта с возвратом исходной ветки.

4. **Мультиагентная защита.**
   Уникальный активный забег на исполнителя (индекс в БД), атомарное бронирование, «одна карточка в работе на держателя», lease и reclaim. Есть тест «два процесса не бронируют одну карточку дважды».

5. **CLI-контракт.**
   `--json` у всех команд, строгие флаги (неизвестный — ошибка), коды выхода 0/1/2/3, цвета только в TTY, `NO_COLOR`, никаких внешних зависимостей, TypeScript без сборки.

6. **Поставка.**
   Версия в `tools/board` как submodule, глобальный диспетчер, `init`/`upgrade`, запрет молчаливого даунгрейда, `doctor`.

7. **Интеграция с OpenCode.**
   Четыре навыка, `/review`, `/spec-review`, `/setup`, плагин, read-only ревьюер, блок в `AGENTS.md`. Сгенерированные файлы в репозитории синхронны с шаблонами — проверено.

8. **Тесты и dogfooding.**
   433 теста, включая полный e2e-цикл `init → review → release` в реальном git, миграции и конкурентность. Доска реально использовалась: 109 закрытых карточек, 34 забега, 75 ревью.

## Слабые стороны

### P0 — блокирует выпуск и доверие к данным

1. **Нет тега `v1.4.0`.**
   Локально и на `origin` последний тег — `v1.3.0`. `latestBoardTag()` берёт его, поэтому новый проект получит старую версию, хотя `package.json` и `CHANGELOG` уже 1.4.0. В самом `release` шага «поставить тег» нет. Это главный блокер готовности.

2. **Нет CI и проверки типов.**
   Есть только `node --test`; нет `.github`, `tsconfig`, `tsc --noEmit`, линтера. Node просто вырезает типы — ошибки типов не ловятся вообще. Для 137 файлов это риск.

3. **Нет резервных копий и экспорта.**
   `.board/board.db` — единственный источник истины, он в `.gitignore`; миграция запускается автоматически при любом открытии БД, без бэкапа. Потеря файла = потеря всей истории доски. Нет `backup`/`export`/`import`.

4. **Документация расходится с кодом — и это управляет агентами.**
   - `board --help` не знает `card spec-review`, `amend`, `scope`, `defer/resume`, `run note`; у `setup` только устаревшие флаги.
   - README противоречит себе: в одном месте «`now 2` по умолчанию», в другом «`now 0` по умолчанию» (на деле 0).
   - README всё ещё описывает старую политику ревью («findings становятся отдельными карточками»), хотя 1.4.0 перешла на пакет / `run note` / бюджет.
   - В README устаревший путь `.opencode/skills/board/SKILL.md`, нет `run note`, `card scope add`, нет записей changelog для 1.2/1.3.
   - `/spec-review` не требует явного `card submit`, поэтому после проверки spec владелец не может approve — поток зависает (уже зафиксировано как REVIEW-3).

### P1 — мешает в реальной работе

5. **`card show --json` раздувается.**
   Для `RUN-1` — **76 КБ и 23 события**: каждое событие хранит полный снимок карточки `before/after`, события не чистятся и не пагинируются. Навык `board-spec` вызывает `card show` при каждом разборе. `now 0` аналогично отдаёт полные `body` последних пяти карточек. Это прямая цена контекста агента.

6. **Параллельные агенты упираются в БД.**
   `take` и `finish` держат транзакцию `begin immediate` во время git-операций (`worktree add`, `merge`). При трёх агентах и `busy_timeout = 5000` возможен сырой `SQLITE_BUSY` вместо понятной ошибки. Файловый lock в `terminology.ts` ждёт 2 с и **не умеет определять устаревший lock**: падение процесса оставляет `.lock`, и все записи терминологии ломаются до ручного удаления.

7. **2-часовой lease молча снимает работу.**
   Любой `now`/`doctor` вызывает `reclaimExpired` и освобождает `in_progress`-карточку. `touch` есть, но **ни один навык о нём не упоминает**. Задача дольше 2 часов теряет карточку, и её может забрать другой агент. Ветка/worktree остаются, но `finish` уже не пройдёт.

8. **Согласованность git ↔ БД при сбое.**
   `finish`/`release` сначала делают merge, потом пишут в БД. Падение между шагами оставляет `dev` изменённым, а карточку — в старом статусе; повторный `finish` может приписать неверный `merge_commit`. Отдельной команды восстановления нет.

9. **`release` доверяет кэшу `in_dev`.**
   Гейт читает флаги из БД, а не пересчитывает их из git; `refreshMergeState` вызывается уже после merge. Ручной merge или рассинхрон может пропустить непроверенный код в `main`.

10. **Плагин не паритетен CLI.**
    Через `board_*` недоступны `card scope add`, `card step/ref/dep`, `run note`, `queue`, `doctor`, глобальный `release`, `touch`, `init/upgrade`. Навыки при этом предписывают именно эти команды — агент вынужден идти в shell, а значит зависеть от `board` в PATH.

11. **«Read-only ревьюер» — только на словах.**
    У `board-reviewer` запрещён edit, но разрешён `shell: "*"`, то есть он может выполнить `board review finding` или `board card add`. Вся политика «ревьюер не создаёт карточки» держится на промпте, не на правах.

12. **Spec review обходится при promotion.**
    Запрос, взятый в забег, продвигается вторым `take` без `assertSpecReview`. Настройка `specReview.mode` для таких карточек не применяется.

### P2 — полировка

13. `--as owner` — самообъявление: approvals и release не защищены от агента, который напишет `--as owner`. Для локального доверенного контура нормально, для команды — нет.
14. Ветки `main`/`dev` захардкожены (`resolveBranches` игнорирует корень). Проекты с `master`/`develop` не подключатся без переименования.
15. `noteRun` перезаписывает `runs.note`: второй проход ревью и причина `run release` теряются.
16. `review list --json` не отдаёт `runId` (лишний вызов), дублирует `spec`/`body` и `plan`/`steps`.
17. Бюджет ревью («до 3 important», «не больше 7») нигде не проверяется — только текст в промптах.
18. `.opencode/agents/` в `.gitignore`: конфиги worker-агентов не воспроизводятся из клона; `board-reviewer.md` пересоздаётся только `init --refresh`/`setup`.
19. Нет `LICENSE`, `repository`, `author` в `package.json`; `bin` указывает на `.ts`, что для Windows-поставки через npm не работает (спасает только `board.cmd`).

## Вердикт

- **Для ежедневной работы в одном проекте на одной машине — да**, после закрытия P0. Ядро уже крепче, чем у большинства самодельных трекеров: правила не размазаны по промптам, а зафиксированы в схеме и переходах.
- **Как поставляемый инструмент для произвольных проектов — пока нет.** Новый проект получит 1.3.0; CI и типов нет; база не бэкапится; документация местами врёт; мультимашинной работы и реальной авторизации нет.
- **Для команды с недоверенными агентами — нет**: `--as` подделывается, ревьюер имеет shell.
- **Для проектов с `master`/`develop` — нет** без правки `resolveBranches`.

## Что сделать первым

1. `git tag v1.4.0 && git push --tags` и добавить тегирование в процедуру release — 5 минут, снимает главный блокер.
2. CI: матрица Node 24/26, `node --test`, `tsc --noEmit` (добавить `tsconfig` и `typescript` в devDependencies).
3. Привести `README` и `board --help` к одной таблице команд; тест должен проверять не только имена команд, но и подкоманды/флаги.
4. `card show` по умолчанию без событий, события — `--events --limit`; в `review list` убрать дубли `spec/body` и `plan/steps`, добавить `runId`.
5. `board backup` / автоматический `.bak` перед миграцией; экспорт доски в JSON/Markdown.
6. `release`: пересчитывать `in_dev` из git до гейта; сделать `finish` идемпотентным или дать команду восстановления.
7. Concurrency: проверять возраст/PID lock-файла, превращать `SQLITE_BUSY` в понятную ошибку, продлевать lease автоматически или упомянуть `touch` в навыках.
