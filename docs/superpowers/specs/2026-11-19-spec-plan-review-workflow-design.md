# Spec, plan и ревью карточки — дизайн

Дата: 2026-11-19
Статус: на утверждении
Связанный документ: `docs/superpowers/specs/2026-11-19-toolbox-board-design.md`
(уточняет §8.4, §9, §10 и §14).

## 1. Зачем

На реальном проекте забег из трёх карточек на модели Max прошёл ревью три
раза. Ревью находило замечания к каждой карточке, карточки переоткрывались,
и цикл `reopen → fix → review` повторялся. Это даёт качество, но стоит много
времени и токенов.

Причины:

- разбор карточки смешивает spec и plan: `body` и `steps` заполняются одним
  проходом, без отдельного решения «что именно должно получиться»;
- у ревью нет критерия остановки: ревьюер может находить улучшения
  бесконечно;
- plan пишется до того, как карточка попала в забег; пока она ждёт
  зависимости и очередь, `dev` уже меняется, и plan устаревает;
- переоткрытие карточки запускает повторное ревью всей карточки, а не только
  исправлений.

Цель — перенести акцент на spec и критерии приёмки, писать plan перед
исполнением, закрывать забег за один цикл ревью и складывать неблокирующие
замечания в отдельные карточки.

## 2. Цели, не-цели, анти-цели

### Цели

- Разбор запроса похож на брейншторм: сначала вытащить всё у владельца,
  затем spec с критериями приёмки, затем ревью spec, затем утверждение spec
  владельцем.
- Владелец утверждает **spec**, а не plan.
- Plan пишет исполнитель при `take`, когда видны актуальный `dev`,
  завершённые зависимости и код.
- Spec review проверяет полноту: можно ли по spec написать plan, не угадывая.
  Если spec неполный, агент сначала пытается дополнить его сам, затем задаёт
  вопросы владельцу.
- Run review проверяет две вещи: соответствие plan и сам код.
- Один цикл ревью на карточку: неблокирующие замечания становятся отдельными
  карточками, а не поводом переоткрыть исходную.
- Режимы ревьюеров настраиваются в мастере настроек и учитывают режим модели
  (Max/High), если его можно определить.

### Не-цели

- Авто-ран без участия владельца.
- Порождение субагентов из CLI: это делает OpenCode-команда или агент.
- Утверждение plan владельцем.
- Полная замена модели карточек; существующие карточки, очередь, lease и
  зависимости сохраняются.
- Автоматическая оценка качества кода без ревьюера.

### Анти-цели

- Бесконечный цикл ревью и «ещё одно улучшение».
- Устаревший plan, написанный за несколько шагов до исполнения.
- Молчаливое изменение scope или поведения после утверждения spec.
- Единственный гейт качества — самопроверка кода тем же агентом.

## 3. Термины и отображение на текущую модель

| Термин | Значение | Сейчас |
|---|---|---|
| **Spec** | Что и зачем нужно, границы, ограничения и критерии приёмки. Контракт владельца и исполнителя. | `cards.body` |
| **Критерий приёмки** | Проверяемое утверждение, по которому принимается результат. Один критерий — одна строка. | нового поля нет |
| **Spec review** | Проверка полноты spec до утверждения владельцем. | нового шага нет |
| **Plan** | Как исполнитель сделает spec: шаги, файлы/scope, проверки. Пишется при `take`. | `steps` + `scope` |
| **Run review** | Ревью в конце забега: соответствие plan и код. | `review` + `/review` |
| **Finding** | Замечание ревью, оформленное отдельной карточкой. | есть |
| **Backlog** | Findings, не блокирующие текущую карточку и release. | не формализовано |
| **Fix run** | Обычный забег, собранный из finding-карточек после их утверждения. Отдельной сущности нет. | — |
| **Reviewer model** | Модель ревьюера: тот же provider/model, что у основной сессии, но без варианта `max`/`high` — default-вариант. | — |
| **Reopen** | Возврат карточки в очередь, если результат не соответствует spec/plan. | есть |

Пользовательские тексты и документация используют `spec` и `plan`.
Внутренние имена `body`/`steps` можно сохранить в v1, чтобы не ломать JSON и
схему; в JSON карточки (`card show`/`card list`) добавляются поля-алиасы
`spec` и `plan`. Полное переименование колонок — отдельное решение, не
обязательное для этого дизайна.

## 4. Процесс

### 4.1 Разбор запроса

1. Запрос создаётся как обычно: `card add`.
2. Агент берёт запрос в разбор: `card shape`.
3. Если в запросе есть открытые вопросы, агент вытаскивает ответы у владельца
   (`ask`, `block`) — как в брейншторме. Пока вопрос открыт, карточка
   `blocked`; разбор не продолжается.
4. Агент пишет **spec**: problem/why, желаемый результат, non-goals,
   ограничения, зависимости, риски и критерии приёмки.
5. Если spec неполный, агент сначала пытается дополнить его из контекста
   проекта. Если ответа в проекте нет — задаёт вопрос владельцу. Угадывать
   нельзя.
6. Запускается **spec review** (режим ниже).
7. `card submit` отправляет spec владельцу на утверждение. Без spec,
   критериев приёмки и пройденного spec review (если он включён) submit
   отклоняется.
8. Владелец делает `card approve` или `card reject`. Approve означает
   утверждение **spec**, а не plan.

### 4.2 Исполнение

1. Утверждённая карточка попадает в очередь и ждёт зависимости.
2. `run start` бронирует карточки; `take` переводит карточку в работу.
3. Перед кодом исполнитель пишет **plan**: шаги, файлы/scope, проверки,
   отображение критериев приёмки на шаги.
4. Если plan требует изменить scope или поведение — это не «план поменялся»,
   а возврат к spec: `block`/`ask` владельцу, при необходимости spec
   обновляется и утверждается заново.
5. Исполнитель выполняет plan, отмечает шаги, делает `finish`.

### 4.3 Ревью в конце забега

1. `run end` определяет режим run review и закрывает забег сразу; ревью не
   блокирует закрытие.
2. Ревьюер проверяет:
   - критерии приёмки и соответствие spec;
   - все шаги plan выполнены, scope не превышен;
   - код: корректность, тесты, ошибки, безопасность.
3. Результат:
   - `done` — карточка закрывается. Замечания к коду становятся
     finding-карточками;
   - `reopen` — только если результат не соответствует spec/plan. Не более
     одного переоткрытия на карточку; дальше решает владелец.
4. `critical` findings блокируют `release`; `important` и `other` уходят в
   backlog. Исходная карточка при этом может быть `done`.
5. Finding-карточки — обычные запросы. После shape/approve они могут попасть
   в отдельный **fix run**; `suggestRuns`/`now 1` может предложить такой забег.
   Отдельной сущности `fix run` нет.
6. Повторное ревью после `reopen` смотрит только diff и открытые findings, а
   не весь забег.

## 5. Spec

Spec хранится в `body` (пользовательское имя — `spec`) и содержит:

- problem/why — какую проблему решаем и почему сейчас;
- желаемый результат — наблюдаемый результат для пользователя;
- non-goals — что сознательно не делаем;
- ограничения — платформа, совместимость, запреты, зависимости;
- критерии приёмки — минимум один проверяемый пункт;
- риски и открытые вопросы, если остались.

Для агентов `card shape --from card.json` принимает:

```json
{
  "spec": "...",
  "acceptance": ["...", "..."],
  "skill": "dev",
  "importance": 3,
  "urgency": 2,
  "needs_merge": true,
  "review_required": true,
  "scope": ["src/**", "tests/**"],
  "deps": ["UI-5"]
}
```

`body` остаётся алиасом `spec` для совместимости. `steps` — это plan, но
заполняется он при `take`, а не при `card shape`; в JSON разбора `plan` не
передаётся. Отдельного файла plan нет.

Критерии приёмки обязательны для новых task-карточек. Старые карточки в
`ready`/`in_progress` не блокируются; требование применяется при следующем
разборе.

## 6. Spec review

### 6.1 Режимы

`specReview.mode`:

| Режим | Поведение |
|---|---|
| `none` | spec review не выполняется |
| `self` | тот же агент проверяет spec по чек-листу |
| `subagent` | свежий субагент проверяет spec |
| `auto` | правило по умолчанию: Max/High → субагент; большой spec → субагент; иначе self |

`auto` по умолчанию. Если режим модели неизвестен (CLI запущен без плагина),
`auto` использует правило размера, иначе self. Явные `none`, `self`,
`subagent` — жёсткий выбор владельца.

Правило Max/High — решение владельца. Субагент-ревьюер работает не в `max`, а
на **default-варианте** той же модели (`reviewer.model` без `#variant`). Это
даёт свежий контекст без цены Max. `self` использует основную сессию и её
модель; в мастере можно выбрать `self`, чтобы не запускать субагента.

### 6.2 Размер spec

`specReview.largeSpecChars` — порог в символах, по умолчанию 6000; `0`
отключает правило. Считается длина spec вместе с критериями приёмки. Если
длина больше или равна порогу, `auto` выбирает `subagent`.

### 6.3 Чек-лист полноты

Spec review отвечает на вопросы:

- понятно ли, какую проблему решаем и для кого;
- есть ли наблюдаемый результат;
- все ли критерии приёмки проверяемы;
- описаны ли non-goals и ограничения;
- известны ли зависимости и риски;
- можно ли написать plan, не угадывая.

Если чего-то не хватает, агент сначала дополняет spec сам, затем задаёт
вопрос владельцу. Результат проверки записывается командой
`card spec-review` (см. §11).

### 6.4 Запись и гейт

Spec review записывается в таблицу `reviews` с `kind='spec'`, режимом и
вердиктом `done|reopen`. `card show` отдаёт resolved-режим и причину
(`specReview: { mode, reason }`), чтобы агент знал, как проверять. `card
submit` требует последний `done`-review, если режим не `none`; записанный
`self` не подходит, если требуется `subagent`. Записанный `subagent` подходит
для требования `self` (более сильная проверка).

### 6.5 Версия spec и повторное утверждение

Spec review действителен только для той версии spec, которую проверяли.
`cards.spec_rev` — целое, увеличивается при любом изменении `body`,
`acceptance` или `scope`; `reviews.spec_rev` хранит проверенную версию.
`card submit` и `card approve` принимают только review с текущим `spec_rev`.

- `card reject` увеличивает `spec_rev` и делает прежний spec review
  недействительным.
- После approve менять `body`, `acceptance` или `scope` через обычный
  `card edit` нельзя. Для изменения есть `card amend <ID> --as <id>
  --reason "..."`: он увеличивает `spec_rev`, сбрасывает spec review и
  возвращает карточку в `shaping`; затем снова spec review и approve.
- Если исполнитель при написании plan понял, что нужен другой scope или
  поведение, он делает `block`/`ask`, а не меняет spec молча. Владелец решает,
  нужен ли `card amend`.
- Мелкие редакционные правки spec тоже требуют re-approve: это цена того, что
  spec остаётся контрактом.

## 7. Plan

Plan пишет исполнитель при `take`, а не автор spec. Это правило выбрано, чтобы
plan учитывал актуальный `dev`, завершённые зависимости и уже влитые карточки.

Plan состоит из:

- упорядоченных шагов; каждый шаг содержит действие и проверку;
- файлов/scope;
- отображения критериев приёмки на шаги;
- тестов и команд проверки;
- рисков и известных ограничений.

Plan не должен добавлять новое поведение. Перед кодом исполнитель сам
проверяет, что каждый критерий приёмки отображён на шаг и каждый шаг имеет
проверку. Если без изменения scope/поведения выполнить spec нельзя, исполнитель
останавливается и задаёт вопрос владельцу. Изменения plan по ходу работы
разрешены, но фиксируются в note; финальный plan — то, что проверяет run
review.

Владелец plan не утверждает. Он может посмотреть его в `card show`; если plan
меняет spec — это возврат к утверждению spec.

## 8. Run review и политика одного цикла

### 8.1 Режимы

`runReview.mode`: `none | self | subagent | auto`. По умолчанию `none`
(сохраняет прежнее поведение «ревью после забега выключено»).

`auto`: Max/High → субагент, иначе self. Субагент-ревьюер работает на
`reviewer.model` — default-варианте той же модели, не в Max. `self` разрешён,
но для проверки кода не рекомендуется: независимый ревьюер ловит больше.
`run end` возвращает `reviewMode` и `reviewReason`; `/review` использует их,
чтобы выбрать self или субагента.

### 8.2 Два предмета проверки

Ревьюер проверяет:

1. **Соответствие plan**: все шаги выполнены, scope не превышен, критерии
   приёмки закрыты.
2. **Код**: корректность, тесты, обработка ошибок, безопасность.

Результат plan-проверки записывается как `plan_compliance = done|failed`.
Если plan не выполнен, verdict — `reopen`. Если plan выполнен, verdict может
быть `done` даже при наличии code-замечаний: они становятся findings.

### 8.3 Один цикл

- Findings не переоткрывают исходную карточку. Они создаются отдельными
  карточками (`new`/`request`) и идут в backlog.
- `critical` findings блокируют `release`; `important` и `other` не блокируют.
- Finding-карточки после approve могут собраться в отдельный fix run; это
  обычный забег, не новая сущность.
- `reopen` разрешён только при несоответствии spec/plan. Не более одного
  переоткрытия на карточку; повторное — только решение владельца.
- После `reopen` ревью смотрит только diff и открытые findings.
- Ревьюить карточки по одной, а не пакетом «весь забег». Одна переоткрытая
  карточка не должна тянуть повторный просмотр остальных.

### 8.4 Почему это дешевле

Исходная карточка закрывается за один проход. Критическая находка не
переоткрывает её, а становится отдельной блокирующей карточкой. Мелкие
улучшения не запускают новый цикл. Plan проверяется один раз в конце, а не
переписывается после каждого изменения `dev`.

### 8.5 Лимит переоткрытий

`cards.review_reopens` — счётчик переоткрытий именно из run review. Он не
смешивается с `cards.attempt` (номер ветки/попытки).

- `review submit --verdict reopen` увеличивает `review_reopens` и `attempt`
  (следующий `take` создаёт новую ветку).
- Если `review_reopens` уже `>= 1`, не-владельческий `reopen` отклоняется с
  кодом 2 и сообщением «нужно решение владельца». Карточка остаётся в
  `review`, findings уже записаны; ревьюер не блокирует её и не открывает
  второй цикл.
- Владелец может сам выполнить `review submit --verdict done|reopen --as
  owner` или `card reopen --as owner`. Это единственный путь обойти лимит.
- `card reopen` для такого решения — команда владельца; остальным акторам она
  недоступна. `review submit` остаётся путём ревьюера.

### 8.6 Покрытие run review

`review_required` — карточный флаг. `runReview.mode != none` — настройка
забега. Покрытие:

- `review_required=true` — карточка идёт в `review` всегда;
- `runReview.mode != none` — все карточки забега идут в `review`, даже если
  `review_required=false`;
- `runReview.mode=none` — в `review` идут только карточки с
  `review_required=true`; `/review` может проверить их вручную.

`run end` возвращает `reviewMode` и число карточек на ревью. Если карточек
нет, `/review` сообщает «ревьюить нечего». `runReview.mode=none` не запрещает
ручное ревью уже существующих `review`-карточек.

## 9. Настройки и мастер

`.board/settings.json`, версия 2:

```json
{
  "version": 2,
  "reviewer": {
    "model": "provider/model"
  },
  "specReview": {
    "mode": "auto",
    "largeSpecChars": 6000
  },
  "runReview": {
    "mode": "none"
  },
  "setupAt": null
}
```

`reviewer.model` — `provider/model` без `#variant`: ревьюер работает на
default-варианте. Если поле пустое, CLI берёт модель текущей сессии без
варианта (плагин передаёт её как `BOARD_SESSION_MODEL`). Глобальная модель по
умолчанию (`ctx.model.default()`) — это другая настройка; её не используем
автоматически.

Если `reviewer.model` всё равно пуст:

- явный `specReview.mode=subagent` или `runReview.mode=subagent` — ошибка
  (код 2) при `card submit`/`run end` с подсказкой `board setup
  --reviewer-model` или выбрать `self`;
- `auto` — падает в `self` с предупреждением, чтобы не наследовать Max молча;
- `.opencode/agents/board-reviewer.md` не создаётся, пока модель не задана.

Миграция с версии 1:

- `reviewAfterRun: true` → `runReview.mode = "subagent"`;
- `reviewAfterRun: false`/нет → `runReview.mode = "none"`;
- `specReview` получает `auto` и 6000;
- `reviewer.model` заполняется из текущей сессии/`BOARD_SESSION_MODEL`.

Мастер настройки запускается один раз после `init` в TTY и вручную через
`/setup`/`board setup`. Он объясняет режимы:

- spec review: `auto`, `none`, `self`, `subagent`;
- размер большого spec;
- run review: `none`, `self`, `subagent`, `auto` (проверяет plan и код).

Флаги для агента:

```bash
board setup --reviewer-model provider/model
board setup --spec-review auto|none|self|subagent
board setup --large-spec 6000
board setup --run-review none|self|subagent|auto
board setup --show
```

Мастер показывает, что субагент-ревьюер работает на default-варианте
`reviewer.model`, а `self` — на модели основной сессии.

Если владелец не хочет менять настройку, `/setup` ничего не выполняет.

## 10. OpenCode и определение модели

Плагин получает `sessionID` в контексте инструмента и читает
`ctx.session.get({ sessionID })`. В ответе есть `model.variant` (например,
`max`) и `model.providerID`/`model.id`. Плагин передаёт вариант в CLI через
`BOARD_MODEL_VARIANT`, а модель сессии без варианта — через
`BOARD_SESSION_MODEL` (`provider/model`). CLI использует их при разрешении
`auto` и `reviewer.model`.

Если вариант недоступен (CLI из терминала, ошибка сессии), `auto` работает по
размеру spec, иначе self. Явные режимы не зависят от варианта.

Ревьюер-субагент описывается файлом `.opencode/agents/board-reviewer.md`:

- `mode: subagent`;
- `model: <reviewer.model>` без `#variant` — default-вариант;
- read-only permissions: можно читать, искать и запускать проверки, нельзя
  редактировать файлы.

`/spec-review` и `/review` используют `board-reviewer` для режима `subagent`;
для `self` работают в основной сессии. Если `reviewer.model` не определён,
субагент-режим не должен молча наследовать Max: CLI предупреждает и
предлагает `board setup --reviewer-model` или `self`.

Новые/обновлённые OpenCode-файлы:

- `/spec-review` — оркестратор (`subagent: false`): читает resolved mode; для
  `self` проверяет spec в основной сессии, для `subagent` запускает
  `board-reviewer`, затем `board card spec-review`;
- `/review` — оркестратор (`subagent: false`): читает `reviewMode`; для
  `self` проверяет plan и код сам, для `subagent` запускает `board-reviewer`;
  оформляет findings и `review submit --plan done|failed`;
- `/setup` — мастер режимов; инструмент `board_setup` получает те же флаги;
- `.opencode/agents/board-reviewer.md` — `mode: subagent`, default-модель без
  `#variant`, read-only права (чтение/поиск/проверки, без edit);
- скилл и `AGENTS.md` — процесс, гейты и правило одного цикла.

CLI субагентов не порождает. Команды-оркестраторы запускают `board-reviewer`
через subagent-инструмент OpenCode; CLI только проверяет записанный режим и
вердикт. Статический `subagent: true` не используется: иначе режим `self`
недоступен.

## 11. Команды и данные

### 11.1 Команды

- `card shape` — spec и acceptance; plan здесь не пишется.
- `card show` — отдаёт `spec`, `plan`, `acceptance` и resolved
  `specReview: { mode, reason }`.
- `card spec-review <ID> --as <id> --mode self|subagent --verdict done|reopen
  --note "..."` — записать проверку spec.
- `card submit` — требует spec, acceptance и пройденный spec review.
- `card amend <ID> --as <id> --reason "..."` — изменить утверждённый spec;
  увеличивает `spec_rev`, сбрасывает review и возвращает в `shaping`.
- `take` — исполнитель пишет plan; plan — это steps + scope.
- `run end` — разрешает run review mode, закрывает забег, пишет
  `runs.review_mode` и возвращает `reviewMode`/`reviewReason`. Старые флаги
  `--review`/`--no-review` остаются per-run override: `--review` включает
  `auto` (или `subagent`, если модель ревьюера задана), `--no-review` ставит
  `none`.
- `review submit <ID> --verdict done|reopen --plan done|failed ...` — run
  review; `--plan` обязателен, `done` с findings разрешён.
- `card verdict` — устаревший алиас `review submit`; те же проверки, включая
  `--plan` и лимит переоткрытий. Второго пути записи вердикта нет.
- `review finding` — finding-карточка.
- `setup` — режимы.

### 11.2 Данные

Схема v2 (`meta.schemaVersion = 2`):

- `cards.acceptance text not null default ''` — критерии, по одному на строку.
- `cards.spec_rev integer not null default 1` — версия spec; растёт при
  изменении `body`, `acceptance` или `scope`.
- `cards.review_reopens integer not null default 0` — счётчик переоткрытий
  из run review; отдельно от `attempt`.
- `reviews.kind text not null default 'run'` — `spec|run`.
- `reviews.mode text` — `self|subagent`.
- `reviews.spec_rev integer` — какую версию spec проверяли.
- `reviews.plan_compliance text` — `done|failed|null`.
- `runs.review_mode text` — resolved mode забега.
- `cards.attempt` — номер попытки/ветки; review reopen увеличивает и его.
  Повторный reopen после лимита отклоняется.

Существующие `reviews` получают `kind='run'`; существующие карточки —
`acceptance=''`, `spec_rev=1`, `review_reopens=0`. Старые карточки в
`ready`/`in_progress` не блокируются; требование критериев применяется при
следующем разборе.

## 12. Тесты и критерии готовности

- Режимы: `auto`/`self`/`subagent`/`none`; Max/High; неизвестный variant;
  порог размера; миграция настроек v1→v2.
- Reviewer model: subagent получает `reviewer.model` без variant; self
  использует модель основной сессии; при неизвестной модели нет молчаливого
  наследования Max.
- Spec: submit без spec, без acceptance, без spec review; self vs subagent;
  неполный spec → вопрос владельцу/block.
- Spec revision: правка body/acceptance/scope инвалидирует review; reject
  инвалидирует review; amend возвращает в shaping и требует re-approve;
  submit/approve с устаревшим review отклоняются.
- Plan: пишется при take; учитывает зависимости и актуальный dev; изменение
  scope → block/ask.
- Run review: plan compliance + code; `done` с findings; findings становятся
  карточками; `critical` блокирует release; `important`/`other` — backlog.
- Покрытие: `runReview.mode != none` отправляет в review все карточки забега,
  `review_required` работает и при `none`.
- Один цикл: после `done` карточка не возвращается в review; один reopen,
  второй отклоняется и оставляет карточку в review для владельца; повторное
  ревью — только diff/findings.
- Совместимость: `card verdict` — алиас с теми же проверками; `run end
  --review/--no-review` перекрывают настройку на один забег.
- E2E: забег из трёх карточек, ревью один раз, findings в backlog, release
  блокируется только critical.
- Fix run: finding-карточки после approve собираются в отдельный забег и
  проходят те же spec/plan-гейты.
- Существующие 290+ тестов остаются зелёными.

## 13. Рассмотренные подходы

### 13.1 Кто пишет plan

- **A. Автор spec после approve.** Плюс: контекст автора. Минус: plan
  устаревает, пока карточка ждёт зависимости и очередь; в большом проекте
  почти всегда.
- **B. Исполнитель при take.** Плюс: актуальный dev, зависимости и код;
  меньше переписывания. Минус: исполнителю нужен полный spec; это
  компенсируется spec review и критериями приёмки. **Выбран B.**
- **Гибрид A/B.** Плюс: теоретически лучше для изолированных карточек. Минус:
  непредсказуемо для агентов и владельца. Отклонён.

### 13.2 Политика ревью

- **Полное соответствие, сколько циклов нужно.** Плюс: максимум качества.
  Минус: три и более циклов, дорого. Отклонено.
- **Один цикл, неблокирующие замечания в backlog.** Плюс: предсказуемая
  стоимость, критическое не теряется. Минус: часть улучшений откладывается.
  **Выбран этот вариант.**

## 14. Решения и открытые вопросы

### 14.1 Ответы builder-check

1. **Версия spec.** `spec_rev` растёт при изменении body/acceptance/scope;
   spec review хранит версию; reject инвалидирует review; после approve
   изменения только через `card amend` и повторное утверждение.
2. **Лимит reopen.** Считается `review_reopens`, не `attempt`. Второй
   review-reopen отклоняется, карточка остаётся в `review`; владелец решает и
   может сам вынести вердикт или сделать `card reopen`.
3. **Покрытие run review.** `runReview.mode != none` отправляет в review все
   карточки забега; `review_required` продолжает работать при `none`.
4. **Старые команды.** `card verdict` — алиас `review submit` с теми же
   проверками; `run end --review/--no-review` — per-run override.
5. **Self/subagent.** Команды `/review` и `/spec-review` —
   оркестраторы с `subagent: false`; субагента `board-reviewer` запускают
   только для режима `subagent`.
6. **Пустая модель ревьюера.** Явный `subagent` — ошибка с подсказкой;
   `auto` — self с предупреждением; `board-reviewer.md` без модели не
   создаётся.

### 14.2 Решения, принятые по умолчанию

1. `important`/`other` findings — backlog; `critical` блокирует release.
2. Max/High в `auto` → субагент; субагент работает на default-варианте
   `reviewer.model`. `self` остаётся доступным явным выбором.
3. Большой spec — от 6000 символов (body + acceptance), настраивается; `0`
   отключает правило.
4. Критерии приёмки — текстовое поле, один пункт на строку.
5. Старые карточки в `ready`/`in_progress` не требуют acceptance до
   повторного разбора.
6. `reviewer.model` — модель текущей сессии без варианта; владелец может
   указать другую. Глобальную default-модель автоматически не используем.
7. Любое изменение spec/scope после approve требует `card amend` и повторного
   утверждения.
8. `runReview.mode != none` покрывает все карточки забега; `review_required`
   работает и при `none`.

## 15. Что остаётся builder'у

- Точная схема миграции v1→v2 и порядок команд.
- Имена колонок/алиасов JSON и совместимость `body`/`steps`.
- Формат записи spec review и plan compliance.
- Тексты мастера и `/spec-review`/`/review`.
- Тестовые фикстуры для Max/High и неизвестного variant.
- Генерация `.opencode/agents/board-reviewer.md` из `reviewer.model` и её
  обновление при `setup`/`init --refresh`.
- Реализация одной команды `review submit --plan` без дублирования проверок.
- `spec_rev`, `card amend`, инвалидация review и запрет правок после approve.
- `review_reopens`, owner-override и поведение карточки в `review` после
  лимита.
- Покрытие run review: `finish` должен учитывать `review_required` и
  `runReview.mode`.
- Совместимость `card verdict` и `run end --review/--no-review`.
- Оркестраторы `/review`/`/spec-review` и вызов `board-reviewer`.
